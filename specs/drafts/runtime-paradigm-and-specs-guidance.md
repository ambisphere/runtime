# Accumulated guidance — runtime paradigm and the ten specs

**Status:** draft · **Scope:** consolidates research-team guidance for issues #4 (foundational paradigm) and #5 (vendor adoption) into one planning artifact · **Companion to:** `specs/VISION.md`, `specs/SRS.md`, `RFP.md`, issues #4 and #5 · **Sibling notes:** `specs/drafts/actor-model-prior-art.md`, `specs/drafts/persona-prior-art.md`

This note consolidates the guidance of eleven analysts into one place so the paradigm decision and the ten implied specs can proceed on a shared foundation. It does not write the specs; it records the recommended paradigm, the contradictions resolved along the way, the spec sequence and its critical path, and a per-dimension adopt/reject summary with citations kept visible. Open questions live here as open questions, per VISION principle 5.

## Decision summary

Adopt a **CQRS-shaped hybrid**, stated precisely as:

> **A capability-gated, actor-bounded write side over a per-entity append-only event log, with an ECS-shaped read/query side as a materialized view.**

Three layers, with strict directionality:

1. **Write side (command/ingestion) — capability-gated actor semantics per entity.** Each entity owns a logical mailbox. Semantic events and actions arrive as addressed, capability-checked commands. The entity is the unit of identity, isolation, and fault containment. RivetKit's proven lifecycle (createState/onCreate/onWake/onSleep/onDestroy, sleepTimeout, keepAwake, compound-key addressing, persistent alarms) is adopted here. Capability gating lives at this boundary and only here.
2. **Source of truth — per-entity append-only event log + deterministic reducers.** Reducers fold the log into component state. This is where event-sourcing earns its keep: it is the one mechanism that simultaneously delivers transactional reduction-with-rollback (which the actor model does NOT give for free), the auditability issue #5 demands, and the factual-state-vs-generated-narration separation issue #5 requires.
3. **Read side — component state as a materialized view, queried by renderers and the attention bus.** "ECS-shaped" in its query ergonomics only: entities are IDs, state is a set of typed components/facets, and renderers + attention bus are read-only systems iterating entities by component presence. This makes cross-entity attention routing (issue #4's novel problem) and dashboards/rollups (issue #5) trivial.

### The one correction this synthesis makes to the prior working phrasing

The prior synthesis called this "CQRS over an ECS core." That phrasing is rejected. "ECS core" implies a shared, freely-mutable component store as the system of record with systems writing into it — which is the textbook definition of **ambient authority**, precisely what object-capability security exists to eliminate. You cannot bolt ocap onto a shared-write ECS core without contradicting its semantics. The system of record must therefore be the **append-only event log**, written only through capability-gated entity mailboxes; components are a **derived, read-only projection** (stream-table duality, DDIA ch. 6). This is the single most important framing decision and should be the headline of the ADR.

### The two further decisions that unblock everything

- **Spec the attention bus first.** Its cross-entity query shape dictates the component/facet model, which dictates reducer outputs, which dictates the event envelope. The dependency runs read-contract → component → reducer → envelope, confirming issue #4's sequencing and the actor-model prior-art finding that cross-entity routing is the binding, unsolved constraint.
- **Decide capability model depth.** ocap-from-day-one vs RBAC-now/ocap-later is the one cross-cutting choice constraining the action manifest, adapter API, and privacy boundary at once. See "Cross-cutting tensions" below for the resolution.

## How the contradictions were resolved

The analysts largely converged, but three genuine disagreements surfaced and are resolved here rather than papered over.

### 1. "CQRS over ECS core" vs "actor-write / ECS-read over an event log"

The foundational-paradigm, reducers, and daemon-architecture analysts independently insist the system of record is the **event log**, not a component store. Several other dimensions (renderer, persona) still used the convenient shorthand "CQRS over an ECS core." **Resolution: the corrected framing wins.** Components are never the authority. Where a dimension's notes say "ECS core," read it as "ECS-shaped read-side projection." This is not cosmetic: it is what keeps the ocap write boundary coherent.

### 2. ocap vs RBAC for the capability model

The action-capability and adapter analysts argue for object-capability (macaroon-style attenuable tokens) **from day one**, because the cross-application sharing requirement (Khaos Machine granting LOSWFX narrow authority over one entity) is exactly what RBAC cannot express without a shared identity registry. The foundational-paradigm analyst lists ocap-vs-RBAC as still-open, and the actor-model prior-art note confirms ocap is lineage-specific, not free. **Resolution:** design the boundary to be **capability-shaped** (possessed, attenuable authority — not roles) from day one, but permit the **first host implementation** to be a trivial single-principal keychain / signed-scope token. Spec ocap semantics; defer full macaroon machinery until cross-app delegation is real. This satisfies both camps: the contract is ocap-compatible, the v1 effort is bounded. RBAC-with-accounts is explicitly the wrong default and is rejected.

### 3. "blocking" as an attention rung vs a separate capability/approval concern

The attention analyst proposes a five-rung ladder (quiet → ambient → nudge → prominent → blocking) but flags in its own risks that putting "blocking" in the attention core may smuggle authorization logic into the read side. The action-capability analyst wants human-approval gates modeled as **durable, async approval-requested state**, not synchronous blocking. **Resolution:** keep the human-gate (a capability/approval concern, write side) **distinct** from how prominently it is surfaced (attention, read side). A confirm-required action emits durable `approval-requested` state; the attention bus may rank it as high as it likes — including a persistent `prominent` — without the runtime ever synchronously blocking the daemon. "blocking" as a ladder rung is retained only as a renderer-honored prominence level (a surface MAY render a modal), never as a write-path block.

### Minor reconciliations

- **One shared event log vs per-entity logs:** left open, but the semantic-event-envelope and daemon analysts agree the *ordering contract* is **per-entity total order only** (the entity is the aggregate boundary); no global cross-entity ordering is offered or needed, because the attention bus reads the materialized view, not the raw log. Whether that is physically one partitioned SQLite table or many is a persistence-engine decision deferred to the daemon spec.
- **Determinism source for clock/RNG:** unanimous — non-determinism (timestamps, ids, seeds) is stamped INTO the event at the ingestion boundary; reducers are pure and read only their inputs.

## Cross-cutting themes and tensions

- **The asymmetry that drives the whole design.** Cross-entity visibility is the project's core novelty AND the one thing actors cannot do (confirmed empirically against RivetKit: no "query all actors", only the coordinator-actor anti-pattern); capability boundaries and fault isolation are the one thing flat ECS cannot do. The read/write split lets each paradigm own the side it is strong on. Every dimension restates this.
- **Derived-never-authoritative.** Components, rollups, attention state, persona, and renderer projections are ALL materialized views over the event log. None is a source of truth; all are rebuildable. The recurring failure mode is letting one of them be written directly (a contributor writing a component, an AI summary written back as fact, a rollup authored independently). This must be a structural impossibility, not a guideline.
- **The fact / narration firewall.** Issue #5 §4 demands deterministic factual state separable from AI-generated narration. Every read-side dimension (reducers, renderer, persona, adapter) must carry a provenance/kind tag (`factual` vs `narrated`). Narration is a styling of facts, never an input to any reducer, never written to the log. Surfaces must always be able to render factual-only.
- **Capability-shaped, not role-shaped.** The write boundary is the only place authority is checked, and it is checked by possessed capability, not identity/role. Renderers get zero action authority by default (POLA). Manifest flags (`destructive`, `confirmRequired`) are UX hints, never the security boundary.
- **Local-first scoping discipline.** Adopt the patterns (event sourcing, CQRS, ocap, snapshots) but reject all distributed/cloud machinery (Kafka, external brokers, async cross-process projectors, consensus, sharding, scale-to-zero serverless). Single-process daemon, synchronous in-process projection, embedded SQLite. The daemon owns both sides, so there is effectively no eventual-consistency read-staleness tax.
- **The hybrid-complexity tax (issue #4's named risk).** Running a log + a materialized view means two representations to keep consistent, and inheriting complexity from both paradigms. Mitigation is strict directionality: capability/actor semantics ONLY on the write boundary, ECS query ONLY on the read side, the log as the single seam. Any feature that writes a component directly or queries across actors on the write side is violating the model.
- **Vendor concepts never touch the core.** Khaos Machine (khaosd, KSPD, factory state, agent roles) and LOSWF/LOSWFX live exclusively in the examples/adapter layer as event sources and action targets. Core ships zero domain kinds, event types, actions, or severity vocabulary. This is the principle most at risk under adopter-driven convenience pressure and must be lint-enforced (core code never reads `ext`/`payload` internals; no `khaos.*`/`loswf.*` in core).
- **Specs before code, paradigm choice is itself a spec.** Committing to event-sourcing-as-source-of-truth is a significant architectural decision; record it as an ADR with rationale and visible open questions, gated behind the attention-bus spec landing first.

## Spec sequence and critical path

The critical path is **attention bus → component/reducer model → event envelope → identity → daemon**, with the paradigm ADR wrapping the front and the bundle format closing the rear as an integration pressure-test. Reasoning: the attention bus is the hardest novel problem and its query shape dictates the component model; the component model dictates reducer outputs; reducer inputs define the envelope; identity underpins addressing and rollups; the daemon realizes all of it at the storage layer. Renderer, action/capability, adapter, persona, and privacy attach to this spine.

1. **Paradigm ADR (ADR-0001).** Record the corrected synthesis, the directionality rule, and the open questions. Unblocks all.
2. **Attention routing / interruption policy (#5 spec 7).** Spec first per issue #4. Defines the read-side query contract and the normalized `attention` component schema, which fixes the facet shape everything downstream depends on.
3. **Reducer / state-component model (#5 spec 3).** The projection layer; defines components (the attention facet among them) and the pure-deterministic-reducer contract.
4. **Semantic event envelope (#5 spec 2).** The write-side command shape reducers consume; CloudEvents-shaped + runtime-assigned per-entity sequence.
5. **Entity identity + hierarchy (#5 spec 1).** Addressing (compound keys) and the parent/child relation the read-side rollups traverse.
6. **Daemon / runtime architecture.** Realizes log + materialized view + lifecycle + crash recovery + renderer brokering at the storage layer.
7. **Renderer observation/projection contract (#5 spec 4).** Read-only subscription over the materialized view; three channels (state / attention / persona).
8. **Action / capability manifest (#5 spec 5).** Declarative manifest + capability enforcement; the write-side capability gate.
9. **Local-first privacy / credential boundary (#5 spec 9/10).** Credential-never-in-state, egress redaction, the trust boundary the capability gate enforces.
10. **Adapter / plugin API (#5 spec 8/11).** Anti-corruption layer over the envelope; derive it from two concrete adapters, not in the abstract.
11. **Persona projection (#5 spec 6).** Optional read-side projection; attaches last among read-side concerns.
12. **Entity bundle / package format (#5 spec 10).** Specced LAST; it depends on eight of the other nine and is the integration test of whether all contracts serialize cleanly.

## Per-dimension guidance

### Foundational paradigm (critical-path)

**Adopt:** the three-layer hybrid above. Write side = capability-gated actor mailbox; source of truth = per-entity event log + deterministic reducers; read side = component materialized view queried by renderers and the attention bus. Hierarchical entity graph is a relation/component on the read side, not actor-to-actor links on the write side. Follow issue #4's sequencing (attention bus first).

**Reject:** "CQRS over an ECS core" framing; ECS as a freely-mutable system of record (ambient authority); a tick/game-loop scheduler (event-driven, reactive observers instead); ocap as mandatory for v1 (capability-shaped, RBAC-degenerate-case acceptable to start); any Khaos/LOSWF concept in the core paradigm.

**Prior art (visible citations):** RivetKit (adopt lifecycle/hibernation/addressing/alarms; reject coordinator super-actor, serverless transport, RBAC-as-the-model) — `specs/drafts/actor-model-prior-art.md`, github.com/rivet-dev/rivet. Bevy ECS with Observers (adopt entities-as-IDs + reactive push-based observers as proof event-driven ECS is production-real; reject ECS-as-system-of-record, tick scheduler) — bevyengine.org, PR #10839. CQRS + event sourcing, Kleppmann DDIA ch.6 stream-table duality, Azure Architecture Center (adopt read/write split, log-as-truth, snapshots; reject Kafka/external bus/async projectors). Object-capability model — Dennis & Van Horn 1966, Spritely Goblins, Murray's *Analysing Object-Capability Security* (adopt no-ambient-authority as the write-boundary design test; reject OCapN networking and full-runtime dependency). Calm Technology, Weiser & Brown 1996 (adopt center/periphery frame for read-side ranking; reject drift into a built-in persona system).

**Open questions:** where non-deterministic narration lives (leaning: a separate non-authoritative projection component, never written to the log); ocap-vs-RBAC depth for v1; materialized-view rebuild cost vs snapshot-from-day-one (needs a DDIA spike with realistic Khaos/LOSWF event rates); whether read authority and write authority are separately gated (attention bus likely sees a redacted/projected facet, not raw state); per-entity log vs one shared partitioned log; whether the attention bus itself must be auditable.

### Attention routing (critical-path — spec first)

**Adopt:** attention as derived read-side state, not pushed events — reducers write a minimal normalized `attention` component (`urgency`, `importance`, `decay`, `state`, `actionability`, `defer_until`/`snooze_until`, `lifecycle`); the bus is a system that ranks entities carrying it; surfaces observe and pull a ranked view. Ranking = a cost-benefit score adopted from Horvitz (keep the math, drop the probabilistic sensing), explainable for audit. An escalation ladder (quiet → ambient → nudge → prominent → blocking) with bounded deferral and a default bias DOWN the ladder. Operator-selectable context/focus modes (`flow` / `operational` / `away`) as a first-class policy input multiplying interruption cost. "Show me what matters now" = a ranked read query over the projection. Surface-specific rules via a capability/affordance map (each surface declares which rungs it honors). Snooze/defer/acknowledge are capability-gated commands on the write side, logged as events.

**Reject:** a notification system / notification OS; inferred or sensed user attention (no ML/Bayesian focus detection — context is explicitly operator-selected, for privacy and determinism); attention as authoritative state; per-renderer attention engines; persona/narrative/tone in the ranking; domain-specific severity vocabulary in core (`release-critical` maps in via adapters); guaranteed-delivery alerting; treating "blocking" as a write-path block (see contradiction 3).

**Prior art:** Weiser & Brown calm technology 1996 (adopt center/periphery, periphery-default, recentering-as-pull; reject physical-embodiment bias). Amber Case, *Principles of Calm Technology* 2015 (adopt smallest-attention, fail-gracefully-to-glanceable; treat as heuristics not spec). Horvitz et al. attention-sensitive alerting / bounded deferral, Microsoft Research (adopt cost-benefit scoring + bounded deferral + context as first-class; reject sensor-based attentional-state inference). Arroyo/Selker + interruptions.net survey arXiv 1806.06771 (adopt match-attentional-draw-to-utility; reject device-centric framing). RivetKit (negative result: confirms attention must NOT be an actor; alarms as prior art for time-based escalation).

**Open questions:** ordinal vs continuous urgency scale; who owns cost-benefit weights and mode definitions (layered, operator overrides bundle — precedence must be specced); hierarchy rollup rule (max-of-children vs weighted-sum vs adapter-defined); escalation-over-time via per-entity alarm vs age-at-query (DDIA spike); whether "blocking" belongs in the attention core at all; minimum context-mode set and whether mode is global or per-entity-group (a desktop running creative Khaos flow and an operational LOSWF release simultaneously may break a single global mode); graceful-degradation fallback when the ranked stream is unavailable; pluggable vs fixed-with-tunable-weights ranker.

### Semantic event envelope (critical-path)

**Adopt:** a first-class semantic (not log-text) event — an immutable, append-only, capability-gated fact addressed to an entity. CloudEvents-shaped envelope split three ways: ENVELOPE (domain-agnostic metadata: `id`, `entity`, `type` reverse-DNS past-tense, `source`, `specversion`, `time`, `subject`, `dedupeKey`, `traceparent`, privacy/redaction hint); PAYLOAD (`data`, schema-on-read, `dataschema` resolved against the bundle); RUNTIME-ASSIGNED (per-entity monotonic `sequence`, `ingestTime`, durability position — producers propose, the daemon is the sole authority for ordering). Per-entity total order only. Append-only local log as system of record, fsync-on-commit before ack, SQLite default. A single capability-gated `submit(event)` mailbox as the only write path; at-least-once delivery + dedupe = effective exactly-once apply. Hard line: events are FACTS; commands/actions are a SEPARATE primitive whose RESULTS become fact events; narration is never a fact.

**Reject:** a transport/wire protocol (adapters normalize SSE/JSON-RPC/FS-watch into the shape); a distributed log or broker (no Kafka/partitions/consensus); global cross-entity ordering; the command/action model (separate spec); AI narration as a fact; log-text/structured-logging ingestion (an adapter responsibility); trusting producer-assigned sequence/time.

**Prior art:** CloudEvents v1.0 CNCF (adopt envelope-vs-data split and core attributes; reject HTTP/Kafka binding modes and its silence on ordering/durability — add sequence + log + ingestion boundary). Event sourcing / DDIA stream-table duality (adopt immutable log, per-entity sequence, snapshots, versioned schemas; reject distributed event-store machinery). Domain events vs commands, DDD (adopt fact-vs-command separation; reject aggregate/repository ceremony). RivetKit (adopt compound-key addressing with injection safety; reject the assumption rollback comes free). At-least-once + idempotent ingestion, Kafka/EventBridge semantics (adopt dedupe-on-key; reject distributed exactly-once).

**Open questions:** the aggregate boundary for ordering (does a parent rollup get its own stream or derive purely from child component state?); thin vs fat default (event-carried-state-transfer needed for un-re-queryable externals like GitHub/CI); schema governance (bundle-owned, leaning yes); schema evolution policy (type-version vs `dataschemaversion` vs upcast-at-replay — must be decided before any log is written); retention/compaction policy; ingestion backpressure/rate-limiting; out-of-order/late events (reducers key on `sequence` for determinism but recency wants event-time — both must be in the contract).

### Reducers and state provenance (critical-path)

**Adopt:** one durable append-only ordered log per entity as the single source of truth; component state as a derived view. Reducers are PURE, DETERMINISTIC `reduce(prevState, event) -> {nextState, provenance}` — byte-identical on replay; no `Date.now`/`Math.random`/IO; all non-determinism arrives inside the event. Provenance/lineage is a first-class output of every reduction (event id, source adapter, ingestion time), modeled on W3C PROV (entity/activity/agent, wasGeneratedBy/wasDerivedFrom/wasAttributedTo). Absolute separation of factual state (deterministic reducers only) from AI narration (a separate, explicitly-tagged projection that reads facts, carries model/prompt/confidence provenance, and is never a reducer input). Components addressable as discrete facets. Per-projection checkpoint (last-applied position) so views are rebuildable and idempotent.

**Reject:** a general-purpose database/query engine exposed to renderers; mandating event-sourcing on adopters' own systems; distributed consensus/replication; runtime AI fact-checking; inventing a new provenance standard; a transactional rollback engine in the actor sense (correctness from pure total reducers + append-only log + replay); vendor component names/event types/reducer logic in core.

**Prior art:** event-sourcing/CQRS projections — eventsourcing.readthedocs.io, event-driven.io, Azure/AWS (adopt log-as-truth, checkpoints, idempotent upsert, rebuildable read models; reject broker-centric delivery). W3C PROV-DM (adopt the triad and relations as lineage vocabulary; reject full RDF/OWL serialization). Datomic/XTDB (adopt accumulate-only facts, as-of queries, bitemporal valid-vs-transaction time; reject adopting the products or Datalog as the renderer surface). Redux reducers (adopt purity discipline; reject single global store). LLM attribution research arXiv 2411.01022 (adopt: untraceable narration = hallucination, require citations to factual components; reject runtime LLM-judge as a core dependency). RivetKit durable state (confirms durable state is proven; reject the assumption rollback/event-sourcing is free).

**Open questions:** snapshotting (must be a pure function of log-prefix, verifiable against replay, never a second source of truth); log retention vs audit; provenance granularity (per-field/component/event — minimum viable for "why is this blocked?"); bitemporal scope for v1; reducer/component schema evolution (versioned reducers vs upcasting); exact narration-provenance fields; cross-entity rollup determinism (reducer over merged stream vs attention-bus/query concern — boundary with attention spec unclear); whether a reduction can legitimately fail (leaning: malformed events rejected at the capability gate, not mid-reduction).

### Renderer contract (high)

**Adopt:** a one-way observation/projection contract, not a UI API. Renderers are subscribers, never authorities (LSP `publishDiagnostics` model — server owns truth and pushes; no `getState()` on the hot path, pull only for snapshot/resync). Three named channels: state projection, attention signals, persona projection (so a tray subscribes to state+attention, a companion to all three). A `RendererPort` driven port in the outermost ring; core runs headless with zero renderers. LSP-style capability negotiation at attach (surface kind, persona support, max prominence honored, projection-schema version; ignore unknown fields). Projection = a daemon-computed view-model, NOT raw components (different surfaces are different projections of the same entity). Subscription by predicate over the read model, with initial snapshot + incremental deltas + monotonic version for gap detection + cheap full resync. Action invocation flows back through the WRITE side, not the renderer port; action affordances + capability metadata ride in the projection as advisory only.

**Reject:** a rendering/layout/animation engine or UI toolkit; a mandated wire protocol (at most one reference binding for testing); renderers holding/mutating authoritative state; the action execution path; the attention-ranking algorithm; persona content/authoring; a general query/analytics API; any vendor surface in core.

**Prior art:** LSP 3.17 (adopt authoritative-server/decoupled-multi-client push, capability handshake, forward-compat degradation; reject request/response orientation and document model, no JSON-RPC mandate in core). CQRS read models (adopt multiple projections from one log, per-surface view-models; reject distributed projection infra). Clean Architecture / ports-and-adapters (adopt RendererPort as a driven port, headless core; reject full onion/DDD ceremony). Calm Technology (adopt prominence-as-daemon-decision surfaced per-surface; treat as the why, not a wire format). RivetKit connection model (counter-example: onConnect/onDisconnect assumes active clients — wrong for passive observers; adopt snapshot+delta+resync instead).

**Open questions:** delta vs full-snapshot transport (likely full for small entities, deltas opt-in for high-frequency — DDIA spike); the canonical reference push transport (SSE/local socket/in-process/gRPC); projection computation locus (per surface-class daemon-side keeps renderers dumb but risks leaking presentation into core); surface-taxonomy ownership (fixed enum vs open registry vs free-form capability strings — keep semantic, not presentational); how much action metadata rides in the projection vs fetched on engage; cross-surface consistency guarantee; backpressure/slow-renderer policy (latest-wins almost certainly right for ambient state); whether chat history/artifact queries extend the observation contract or are a separate query surface.

### Action / capability (high)

**Adopt:** two separate layered specs — (A) a DECLARATIVE ACTION MANIFEST (per-action: `id`, `title`, `description`, JSON-Schema `inputSchema`/`outputSchema`, behavioral flags `confirmRequired`/`destructive`/`idempotent`/`locality:local|remote`, `requiredCapabilities` as authority tokens not role names, `preconditions` as a predicate over component state, `resultEvent`s that flow back into the log) borrowed from MCP tool definitions; (B) a CAPABILITY ENFORCEMENT MODEL borrowed from the object-capability lineage. Authority is a possessed, unforgeable, attenuable token, not an identity check; macaroon-style serializable tokens with caveats (offline-verifiable, attenuable, inspectable) for cross-process delegation; POLA (renderers get zero action capability by default); revocation via caretaker/membrane indirection. Manifest flags are UX/attention HINTS, not the security boundary — the capability check at the write boundary is the boundary. `confirmRequired`/`destructive` emit durable `approval-requested` state (async, mailbox), surfaced by attention, never a synchronous block.

**Reject:** any concrete vendor action in core; an identity provider / OAuth server / login system; a remote-action transport/RPC protocol; AI/LLM-driven actions by default (chat is one optional caller); a permission/role taxonomy (capabilities are possessed authorities, no global role hierarchy); the confirmation UI; distributed multi-node action consensus.

**Prior art:** MCP tool definitions + annotations (adopt the declarative shape, JSON-Schema in/out, readOnly/destructive/idempotent hints, and MCP's own stance that annotations are untrusted hints not the security boundary; reject model-controlled JSON-RPC-over-HTTP transport and the LLM-as-primary-caller assumption). Object-capability model — E, KeyKOS/EROS, seL4, Goblins (adopt unforgeable attenuable references, POLA, confused-deputy immunity; reject full ocap-language lock-in and ocap-all-the-way-down). Macaroons, Birgisson et al. 2014, libmacaroons (adopt caveat-based attenuation, offline verification, delegation-by-minting-weaker; reject third-party-caveat network round-trips except opt-in for genuinely remote actions). RivetKit actions + permission hooks (adopt actions as named schema-typed write-side operations and the inspector/list-actions pattern; reject its RBAC hooks as the capability model).

**Open questions:** the capability-granting ceremony (daemon keychain vs per-bundle capability file vs grant-on-first-use); capability scope granularity (per-action/entity/kind/resource-pattern); confirm-required synchronous vs durable async (strongly recommend async); precondition evaluation sites (daemon authoritative at invoke + advisory to renderers — one source of truth); whether result events carry invoker provenance for audit (likely yes); where remote-action credentials live relative to the capability (capability authorizes the action; the adapter holds the secret — secrets never travel in the token).

### Entity identity and graph (critical-path)

**Adopt:** two-part identity — a logical address (URI-shaped, human-meaningful, adopter-defined `<namespace>:<kind>/<local-id>[/<sub-id>...]`, modeled as a compound segment list not a joined string, to defeat key-injection) that is an alias onto an internal opaque immutable handle (ULID/UUIDv7, the real ECS id and durable primary key, never reused, survives rename/re-home). Entity KIND as declarative bundle metadata and a component/tag, NOT a class hierarchy. Graph as first-class typed directed edges `(relationType, source, target)` (Flecs/Bevy relationship design generalized to a property graph). Ship exactly two built-in relation types — `child-of` (containment/rollups/cascade) and `instance-of`/`kind-of` — everything else adopter-defined. Wildcard/predicate edge queries on the read side. Rollups as derived read-model state (ClickHouse-style incremental bottom-up aggregation, rules declared per-kind), never authored. Cleanup/cascade policy as configurable relation metadata (Flecs lesson), with referential integrity enforced on the handle.

**Reject:** any built-in domain kind (no Issue/PR/Project/Character/Workflow in core); a general-purpose graph query language (Cypher/Gremlin/Datalog) in v1; a distributed/sharded identity authority; identity derived from persona/vendor-account/rendering substrate (reject claude-buddy hash-from-account-id); more than two built-in relation types (resist convenient `blocks`/`depends-on`); attention ranking or persona projection in this dimension; network-resolvable URLs or registered URNs.

**Prior art:** Flecs relationships (adopt relation/target pairs, distinct ChildOf vs IsA, cleanup-as-metadata, wildcard queries, relative name lookup; reject 64-bit-packed encoding and archetype-table internals). OpenTelemetry resource conventions service.namespace/name/instance (adopt the three-part decomposition; reject mutable-best-effort-label framing — identity is an enforced unique index). RFC 8141 URNs + DataHub immutable URNs (adopt persistent location-independent immutable ids as lineage basis; reject the literal urn: scheme and IANA registration). RivetKit compound keys (adopt segment-list addressing + injection warning; reject point-to-point-only addressing). ClickHouse materialized-view rollups (adopt incremental insert-triggered chained aggregation; reject the OLAP engine itself). DDIA graph models + stream-table duality.

**Open questions:** identity rebinding on rename/re-home (retain alias history for redirects vs hard-cut); multi-parent containment (single-parent gives clean rollups; multi-parent needs a defined aggregation/dedup rule); cross-namespace edges (must the capability/privacy boundary gate edge creation into another adopter's subgraph?); rollup determinism vs cost (eager vs debounced vs lazy); whether edges get their own ids/provenance (so an edge can be the subject of an event); local-id uniqueness scope (within namespace+kind, within parent, or globally within namespace).

### Adapter / plugin API (high)

**Adopt:** the adapter layer as an Anti-Corruption Layer — vendor systems are external bounded contexts; adapters translate native events into the semantic envelope and never the reverse. One narrow stable inbound port (emit envelopes addressed to an entity key; optionally subscribe to outbound projection state). The envelope IS the translation target (stable injection-safe compound key, namespaced semantic type, monotonic source offset for idempotent ingestion, occurred-at + ingested-at, provenance tag, fact-vs-narration discriminator; vendor fields in an opaque namespaced `payload` the core never branches on). Capability-gated (not RBAC) write side with macaroon semantics for attenuable delegation. Local-first credential boundary: credentials live with the daemon/adapter, NEVER in entity state, component store, or event log; the envelope carries provenance, not secrets. A hard action taxonomy: LOCAL / REMOTE-READ / REMOTE-WRITE(destructive), default-deny. Per-entity-kind redaction/egress policy applied BEFORE any state ships to a remote model. SemVer + negotiated version handshake on the envelope/port (the frozen public API). WASM Component Model / WIT cited as a FUTURE path for untrusted third-party adapters, not adopted now.

**Reject:** a vendor SDK or Khaos/LOSWF code in core; a second event/data model (the API is a thin contract over the envelope); a network authorization protocol (capability tokens are internal local-first authority); a mandatory plugin sandbox/WASM runtime now; remote/cloud sync or a centralized credential store; distributed-commit guarantees across adapters; defining the AI provider/prompt/summarization stack (redaction governs the boundary; the provider is just another capability-gated remote adapter).

**Prior art:** Anti-Corruption Layer (DDD / Azure / Clean Architecture — adopt defensive translation + dependency-rule inversion as the "adopt without forking" mechanism; reject heavyweight per-pair ACL infra and over-abstracting before 2+ real adapters). Macaroons (adopt HMAC-chained caveats, offline attenuation, third-party caveats as human-approval discharge; reject cloud-distributed framing). Object-capability / POLA (adopt the principle via macaroons; reject requiring a full ocap object graph). RivetKit ActorDriver/ManagerDriver + compound keys (adopt driver-abstraction-as-port precedent and injection-safe keys; reject RBAC hooks as the model, serverless execution, Rivet cloud). WASM Component Model + WIT (future direction only). SemVer 2.0.0 + contract testing. DDIA stream-table duality / event sourcing (adopt source-offset + idempotency, envelope-as-long-lived-contract; reject two-phase-commit and free-rollback assumptions).

**Open questions:** canonical capability token format (macaroons wholesale vs simpler signed-scope now); where credentials physically live (OS keychain vs daemon-encrypted store) and how an adapter presents a credential reference without the daemon holding the raw secret; where redaction policy is declared (bundle vs action manifest vs separate egress spec — likely spans all three); trust tiering (in-process first-party vs sandboxed third-party); how an adapter discovers permitted namespaces (static declaration validated against capability vs dynamic negotiation); push-only vs pull/backfill for historical replay (e.g. GitHub issue history on first connect); where the fact-vs-narration discriminator lives and who may write narration (likely only AI-egress adapters); what issues the discharge for human-approval caveats.

### Local-first privacy / credential boundary (high — extracted across dimensions)

Several dimensions converge on a standalone privacy/credential spec even though no analyst owned it solely. **Adopt:** credentials never in entity state, components, or the event log — only a capability/credential reference travels; the adapter holds the secret. Egress to any remote model/provider is an explicit boundary owned by the adapter layer, with opt-in per-entity-kind redaction applied before egress and a record of what was sent. Read authority and write authority separately gated (the attention bus and cross-entity queries likely see a redacted/projected facet, not raw entity state). Namespace as the trust/privacy boundary; cross-namespace edges and events must respect it. **Reject:** centralized credential stores, cloud sync, sensor-based attention inference. **Open questions:** the exact redaction-policy home; whether the privacy boundary is enforced at the projection layer (attention sees a redacted facet) and how that is specced. This should be specced alongside the action manifest and adapter API since all three reference it.

### Persona projection (medium)

**Adopt:** persona as a PURE, OPTIONAL, DERIVED projection — `project(entityState, attentionState, capabilityPolicy, surface) -> personaProjection` over read-only views; output is presentational/expressive metadata holding NO authoritative state. Three layers: reducers own semantic states, persona maps them to expressive states, renderers map those to frames — each replaceable. Optional and additive (operational entities run with zero persona; a formal null/factual projection is the shared default). Layered cascade resolution (product default → entity-kind → state/surface → instance), adopting design-token three-tier architecture. Hard wall between factual and narrated via a per-field provenance/kind tag; renderers must be able to render factual-only. Surface-aware tone that consumes attention state but never decides interruption (attention has final authority). Persona rules ship in the bundle as declarative content referencing the declared semantic-state vocabulary.

**Reject:** a personality/character/mood-engine or companion product (VISION non-goal); persona as a source of truth or a reducer-written component; persona as required; persona as the attention or capability authority; a renderer/animation-state vocabulary (no spritesheet/atlas in the persona contract); vendor identity (no hash-from-account-id, no Khaos/LOSWF persona in core); a mandatory AI feature.

**Prior art:** codex-pets / hatch-pet / claude-buddy via `specs/drafts/persona-prior-art.md` (adopt state-vocabulary-as-contract, self-contained bundle, hatch authoring, optional depth fields; reject spritesheet-as-truth, nine hardcoded animation states, `$CODEX_HOME` lock-in, hash-from-account-id determinism, single assumed channel). Design tokens — Material 3, Brad Frost (adopt primitive→semantic→component cascade and white-label override; reject the styling-only assumption — persona must carry provenance tokens lack). CQRS read-model projections (adopt persona as one more independent projection; reject treating it as on the critical write path — it must never gate capability-critical signals). Calm Technology — Weiser & Brown, IDEO, CEUR ambient-display work (adopt tone-matches-purpose-and-context; reject device-specific tone). LLM grounding/provenance research arXiv 2411.01022 (adopt structural factual-vs-generated separation; reject heavyweight RAG fact-checkers in core).

**Open questions:** minimum persona projection schema (no renderer fields); where the cascade resolves (daemon-side for consistency + single provenance audit point vs renderer-side for surface autonomy — likely daemon resolves semantic+attention, renderer resolves styling); how to keep persona rules declarative without a Turing-complete DSL (the "personality system" non-goal risk); how narrated phrasing is bounded to reference only declared factual fields (template slots validated at authoring time); whether persona needs capability-policy access directly or only a pre-resolved "available safe actions" view (prefer the latter); whether a formal null-persona projection should be first-class (argues yes).

### Daemon / runtime architecture (critical-path)

**Adopt:** a single long-running local host process that owns all entity state and is the sole writer to the durable append-only event log; component state is a derived materialized view rebuilt from the log. SQLite in WAL mode as the default engine for both (one append-heavy events table, per-component projection tables), behind a StorageDriver interface. RivetKit's lifecycle vocabulary and hibernation (Cold → Warming → Warm/Active → Cooling → Cold; wake on inbound event, persistent alarm, or a query needing live derivation). Snapshot periodically and on clean sleep to bound replay cost. A lightweight always-resident index of identity/kind/edges/last-known-attention-summary so the attention bus and dashboards do cross-entity rollups WITHOUT waking cold entities (the key move that resolves the attention-vs-isolation tension at the storage layer). Two-layer crash recovery (SQLite WAL auto-replay + application rebuild from last snapshot watermark); deterministic idempotent reducers make replay safe; "transactional reduction with rollback" is spec'd as a storage-transaction property (append + reduce in one txn; on reducer failure the txn aborts, the event is not committed), NOT a paradigm freebie. The daemon as broker: a local-only endpoint (Unix domain socket preferred, 127.0.0.1 loopback fallback); capability-gated addressed ingestion (write); SSE-style one-way resumable subscription with a monotonic cursor (the log sequence) for observers (read); a bidirectional channel reserved only for interactive control/chat. Single-instance via socket-bind + lockfile/PID; supervision delegated to launchd/systemd with a bounded graceful SIGTERM drain.

**Reject:** a distributed/replicated/clustered datastore (no replication/partitioning/sharding/quorum/consensus); a cloud control plane or scale-to-zero serverless host; a bespoke process supervisor; a general-purpose message queue/broker product; a single hard-dependency storage engine (SQLite behind a swappable driver); defining the attention algorithm/envelope/reducer language/capability model here (sibling specs); any Khaos/LOSWF concept in core.

**Prior art:** SQLite WAL (adopt as default embedded engine with auto crash recovery, monotonic rowid as cursor; reject SYNCHRONOUS=OFF for the log, reject hardcoding SQLite into entity/reducer code). RivetKit lifecycle + hibernation (adopt hooks, sleepTimeout/keepAwake, persistent alarms, driver abstraction, state-vs-vars discipline; reject serverless transport, coordinator super-actor, RBAC-as-the-model, Rivet cloud). DDIA storage engines / event sourcing / stream-table duality / fault tolerance (adopt event sourcing, checkpoints, idempotent reducers, design-for-faults; reject distributed machinery). SSE resumable streams + Unix domain sockets (adopt one-way cursor-resumable observation + UDS with loopback fallback; reject Redis/external pub-sub and WebSockets on the read path). systemd/launchd (adopt external supervision, socket activation, bounded drain; reject bespoke supervision and init-system coupling).

**Open questions:** snapshot cadence + log-compaction/retention policy (full-audit vs truncate-behind-snapshots pull opposite ways — DDIA spike); one global event log vs per-entity logs (depends on adopter event volume); exactly what lives in the always-resident cross-entity index (co-design with the attention bus, which must be specced first); whether a query needing live derivation may force a cold entity warm; where the capability check sits relative to log append (reject-before-append vs log-then-validate-with-audit-of-attempts); enforced sole-writer (recommended) vs convention; graceful-shutdown time budget and making in-flight reduction safe under SIGKILL (relying on WAL atomicity — must be specced and tested).

## Top risks

- **The "ECS core" mislabel re-importing ambient authority.** If contributors treat the component store as a freely-writable world (game-ECS instinct), the ocap write boundary becomes incoherent. Mitigation: name it a projection/materialized view, make components structurally read-only outside the reducer, and lint for direct component writes that bypass the log.
- **Hybrid-complexity tax.** Inheriting complexity from both paradigms without the conceptual integrity of either. Mitigation: enforce strict directionality (capability/actor only on write, ECS query only on read, log as the single seam) as a reviewable invariant.
- **Fact / narration firewall erosion.** The easiest shortcut is letting an AI summary write back into a component "because it's convenient," which contaminates factual state irrecoverably and re-egresses hallucinations. Must be a structural impossibility (only egress adapters may write narration; narration template slots restricted to declared factual fields), not a guideline.
- **Vendor leakage into core.** Khaos/LOSWF concepts drifting into core via convenience or the opaque payload being branched on, silently recreating lock-in. Mitigation: lint that core never reads `ext`/`payload` internals or `khaos.*`/`loswf.*` types; vendor everything lives under examples/adapters.
- **Premature paradigm or engine lock-in violating specs-before-code.** Committing to event-sourcing and SQLite are real decisions. Mitigation: record the paradigm as ADR-0001 with visible open questions, gate it behind the attention-bus spec, and keep SQL behind the StorageDriver so reducers/queries never leak SQL.
- **Schema/reducer evolution debt.** Long-lived event logs outlive reducer code; replaying old events through new reducers can break, destroying the rebuild guarantee that justifies the whole design. Mitigation: version the envelope and spec an upcasting/migration + snapshotting strategy before any log is written.
- **Snapshot drift and unbounded log growth.** Snapshots diverging from replay collapse the audit story; unbounded logs are operationally fatal for a long-running local daemon. Mitigation: snapshots must be a pure verifiable function of a log-prefix; a compaction/retention policy that preserves minimum lineage must exist from day one.
- **Over-engineering for the single-user local case.** Event sourcing + ocap + bitemporal + full PROV may be heavier than the common case needs. Mitigation: capability-shaped boundary with an RBAC-degenerate v1, a trivial single-event "current state" degenerate case, conceptual PROV/bitemporal adopted only as needed — never the distributed CQRS infra.
- **Determinism leak.** A reducer or adapter reading wall-clock/RNG/IO silently destroys replayability and the audit trail. Mitigation: inject time/entropy as event fields; enforce with a replay-equality property test or the audit guarantee is fiction.
- **Single-daemon SPOF and a wedged (not crashed) daemon.** All entities go dark and a wedge is harder to detect than a crash. Mitigation: external supervision, a liveness/health endpoint, bounded operations.
